Executive summary

October 2026 was the month the AI developer toolchain became a mainstream target.

On 21 October a malicious release of LiteLLM, an open-source gateway that routes requests to many AI model providers, was published to PyPI and LiteLLM's Docker image tags for about two hours1. It carried a credential stealer that ran whenever Python started, and it targeted cloud keys, model provider keys and AI tool sessions2. LiteLLM traced the breach to an administrative key left in public commit history since May3.

On 29 October two tampered versions of the Claude Code extension were served through Cursor's extension marketplace for roughly 11 hours, planting an attacker's SSH key and persistence on Windows and macOS machines4. Cursor says the versions were not developed by Anthropic, and Microsoft confirmed the official Visual Studio Marketplace and npm channels were not affected4,5. Earlier in the month a hijacked Tensorlake npm release carried a self-spreading worm that harvested AI tool and MCP configuration files6.

The common thread is not a single flaw. Each attack abused a trusted release channel, and each went after the credentials that AI work concentrates on developer laptops, build runners and gateways. Signatures and provenance did not stop them, because the attackers used the projects' own pipelines or listings.

The bottom line
Treat AI gateways, coding assistants, extensions and MCP servers as privileged software. Know where they run, control how they are installed, keep keys scoped and short-lived, and be ready to rotate everything they could reach.

Key findings

Seven things the October incidents tell us

01
Trusted channels were the route in, not software bugs.
The LiteLLM release was built by its own release workflow pointed at a lookalike fork, and the extension appeared under the Claude Code listing in Cursor's marketplace3,4.
02
Leaked secrets started the LiteLLM chain.
An admin key committed in May was deleted within hours but never revoked, and it led to the GitHub tokens used in October3.
03
The payloads were built for AI environments.
Researchers describe stealers that looked for model provider keys, AI tool sessions and MCP configurations alongside cloud and source control credentials2,6.
04
Speed of detection limited the damage, but not to zero.
An external researcher flagged the LiteLLM release about 20 minutes after publication, yet stolen AWS credentials were being tested against Amazon Bedrock within hours, according to Wiz3,7.
05
Signatures and provenance passed.
Compromised LiteLLM images carried a valid signature from the project's old key, and the Tensorlake release carried valid npm provenance1,6.
06
Uninstalling was not enough.
Both the LiteLLM and extension payloads left startup files or persistence that survive removal of the package or extension2,4.
07
This is a pattern, not a one-off.
LiteLLM was compromised for the second time in 2026, after a March incident linked to its CI security scanning tool8.

LiteLLM

From a forgotten key to a poisoned release

The key was deleted from the file within hours. It stayed valid for more than four months.

LiteLLM is popular because it simplifies AI work: one gateway, many model providers, with central management of keys and spend. That role is also what made its compromise serious. Datadog estimates the package sees about 23 million downloads a week2.

According to LiteLLM's root cause analysis, the chain began on 27 May 2026, when a configuration file containing an administrative key for an internal agent platform was committed to a public repository. The file was deleted about three hours later, but the commit stayed in public history and the key was never revoked3.

On 10 October the attacker used that key against the platform's API. A request listing managed agents returned configuration that included the GitHub CLI token of one of two organisation owners. With it, the attacker ran temporary workflows that posted repository secrets, including two other maintainers' tokens, to an external endpoint, then deleted the runs3.

On 21 October the attacker changed LiteLLM's private release workflow so it could build from a different source, overrode branch protection with the owner token and pointed it at a lookalike fork, Berri-AI/litellm. A second token approved the production gate, the poisoned wheels and images were published, and a third token deleted the run records3. LiteLLM also notes it had temporarily widened release permissions that week for bugfix backports1.

LiteLLM's initial notice also said it had seen Claude Code embed a user's GitHub CLI token in response bodies, which could then appear in gateway logs1. That is LiteLLM's observation; The Hacker News noted it had not been independently verified, and we found no public response from Anthropic on the point12.

The payload ran from Python startup files, so it executed whenever Python started, even if LiteLLM was never imported. It encrypted what it found and sent it to a lookalike domain, and an hourly loader was ready to fetch further code, although only test values were seen2. Wiz researchers counted 16 data-harvesting modules13. Enterprise customers on LiteLLM's private release were not affected1.

Extension and worm

An extension, a worm and a familiar playbook

The extension did not need a vulnerability. It ran because extensions run.

The second major October incident hit developers' desktops. Between about 2:27am and 1:35pm Pacific time on 29 October, versions 2.1.312 and 2.1.313 of the Claude Code extension in Cursor's marketplace carried a malicious loader for Windows and macOS. Cursor states the versions were not developed by Anthropic4.

Microsoft's analysis found the loader ran when the extension loaded, before the normal extension code. It gathered host details and the names, not values, of environment variables that looked like secrets, appended an attacker's SSH key, tried to enable SSH and open a reverse tunnel, and set up persistence disguised as system monitoring5. BleepingComputer reported that coding errors meant SSH was not enabled on most macOS and Windows hosts, although key planting and reconnaissance could still occur14.

Cursor removed the versions, shut its entire marketplace as a precaution, audited access, rotated keys and rebuilt the marketplace before bringing it back4. Cursor told reporters at most 5,000 users were affected and that it would contact them directly9. Anthropic staff said the official VS Code and Open VSX channels were unaffected and that Anthropic's systems were not compromised9. How the attacker came to publish under the Claude Code listing has not been publicly explained14.

Early reports that Open VSX also carried the malicious version are disputed. One security firm said it found it there, while others, including Microsoft's analysis, place the incident in Cursor's marketplace only15,5.

The Tensorlake case on 8 October showed the same instinct in package form. A compromised maintainer account pushed code and published tensorlake 0.5.144 through the project's own workflow, so it carried valid npm provenance. Its install hook harvested tokens, cloud keys and AI tool and MCP configurations, then republished itself into other packages the victim could write to6.

Tensorlake's payload also wrote Claude Code and VS Code settings files into repositories so it would run again when a project was opened16, and its advisory warns that it installs a service that deletes the user's home directory if the stolen GitHub token is revoked before the service is removed6.

The attraction

Why the AI toolchain is worth attacking

Compromise an AI gateway and you inherit every key it holds.

The October payloads read like shopping lists, and the lists are revealing. Alongside the usual cloud and source control credentials, researchers found the LiteLLM stealer looking for model provider API keys, sessions for Claude, Codex and Cursor, and the credentials LiteLLM's own proxy database holds for upstream providers2. Tensorlake's worm collected configuration and MCP files for several AI coding tools16.

The reason is concentration. An AI gateway exists to hold many provider keys in one place. A coding assistant runs with a developer's own access to code, shell and tokens. An MCP server is, by design, a bridge from an AI assistant into other systems. Compromise any one of them and you inherit its reach.

Those keys have direct value. Wiz reported that the attacker behind the LiteLLM release validated stolen AWS credentials from CI runners and Kubernetes nodes and checked access to models on Amazon Bedrock, behaviour it linked to LLMjacking, where stolen access is used to run models at the victim's expense7.

Pace adds risk. AI teams update gateways, SDKs and assistants often, to pick up new models and features, and many installs and container tags float to the newest version. A malicious release does not need to survive long if automated builds fetch it within minutes.

Trust adds more. Developers are used to approving extensions and packages from familiar names, and some protections that buyers rely on were not designed for this threat. LiteLLM's compromised images carried a valid signature from its old key, and Tensorlake's release had valid provenance, because both were produced by the projects' own release machinery1,6.

Finally, AI agents themselves are being drafted in. Earlier attacks have tried to use locally installed AI coding tools to search machines for secrets, and Tensorlake's worm used assistant settings files to re-run itself17,16. The tools are both the target and, increasingly, the vehicle.

UK organisations

What it means for UK organisations

The first question in every incident was the same: are we running it?

Few UK businesses write their own AI gateways, but many now run one, often stood up quickly by a data or engineering team to give staff access to several models. Many more have developers using AI coding assistants and editor extensions on laptops that hold cloud and source control credentials. That makes these incidents relevant well beyond the technology sector.

The UK already has a framework for this. The NCSC's supply chain security guidance sets out 12 principles for gaining and keeping oversight of the suppliers your systems depend on22. The Software Security Code of Practice, published by DSIT and the NCSC in May 2025, sets voluntary baseline expectations of software vendors, including how they secure their build environments and communicate with customers23. Open-source projects and extension marketplaces sit awkwardly in procurement, but the principles transfer.

The most common gap we see is basic visibility. When an advisory lands, many organisations cannot say quickly which machines installed a given package version or extension, because developer tooling sits outside the asset and software inventories that IT maintains.

The second gap is how credentials are held. Model provider keys are often long-lived, broadly scoped, shared between projects and stored in environment files. That turns a two-hour exposure window into a long-tail problem, because every key has to be found and replaced.

The third is response. The October advisories were detailed and specific about order: do not start Python in an affected environment, remove persistence before revoking tokens, rotate from a clean machine. Teams that treated them as routine patch notices risked making things worse.

Data protection matters too. If a compromised machine or gateway held personal data or credentials to systems that do, organisations need to assess whether a personal data breach has occurred and whether it must be reported to the ICO within 72 hours under UK GDPR.

Recommendations

Six steps to keep AI tooling trustworthy

In rough priority order. Most need policy and configuration, not new products.
01

Inventory AI tooling

Gateways, SDKs, assistants, extensions and MCP servers, with an owner and what each can reach.
02

Pin, delay and mirror

Pin by version and digest, hold new releases for a cooling-off period, and install from a private registry you can block.
03

Allow-list extensions and MCP servers

Use central admin controls; Cursor, for example, documents publisher allow-lists and install cooldowns24.
04

Shrink the value of keys

Per-application provider keys with spend limits, in a secrets manager, and short-lived tokens for source control and CI.
05

Separate admin from daily use

Owner and admin rights on dedicated accounts, as LiteLLM is now adopting11.
06

Watch behaviour and rehearse

Alert on editors adding SSH keys or startup items, and practise cleaning and rotating in the order advisories prescribe.

Glossary

Terms used in this report

AI gateway
Software that sits between applications and AI model providers, holding provider keys and routing requests.
Supply chain attack
Compromising trusted software, such as a package or extension, to reach its users.
Release pipeline
The automated workflow that builds, signs and publishes a project's packages and images.
Lookalike repository
An account or repository named to resemble a legitimate one, such as Berri-AI for BerriAI.
Image digest
A fixed fingerprint for a container image. Tags such as latest can be moved; digests cannot.
Provenance
Signed evidence of where and how a release was built.
.pth file
A Python file processed when the interpreter starts, which can run code automatically.
Extension marketplace
A store from which code editors install add-ons, such as Open VSX or Cursor's marketplace.
MCP server
A connector using the Model Context Protocol that lets AI assistants use tools and data.
Reverse SSH tunnel
A connection from the victim to the attacker that lets the attacker reach the victim's machine.
LLMjacking
Using stolen credentials to run AI models at someone else's expense.
Worm
Malware that spreads itself, here by republishing into packages the victim can write to.
