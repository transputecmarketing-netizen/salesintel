Foreword

The step from answering to acting is the biggest change in AI since the chatbot.

For most organisations, AI so far has meant an assistant that answers questions and drafts text. A person reads the output and decides what to do with it. Agents change that. They can look things up, update records, raise tickets, write and run code and work through a task from start to finish.

That is a real opportunity. Much of the work that slows teams down is not hard thinking but the steps around it: gathering information, copying it between systems, chasing updates. Agents are well suited to exactly that kind of work.

It also changes the risk. An assistant that gets something wrong produces a bad draft. An agent that gets something wrong can send the email, change the record or delete the file. This playbook shows how to get the benefit while keeping that risk small, visible and under your control.

Introduction

Give AI a job, not just a question.

An agent is AI with tools, a goal and permission to act. Done well, it takes routine work off your people's plates. Done carelessly, it creates a new kind of operational risk. The difference is almost entirely in how you set it up.

Start with narrow, repeatable work

The best first agents do one well-defined job with clear inputs, clear outputs and a person who already owns the process.

Set the level of autonomy deliberately

Decide whether the agent suggests, acts with approval or acts within limits. Start low and earn the right to go higher.

Treat agents like new staff with system access

Give them only the permissions they need, log what they do and review their work until they have proved themselves.

Understanding agents

Model, tools, goal, loop: the four parts of every agent

An assistant tells you what to do. An agent does it. That is why the setup matters so much more.

Strip away the marketing and every AI agent has four parts. There is a model, the language model that reads, reasons and decides what to do next. There are tools, the connections that let it search, read a file, query a database, call an API or update a system. There is a goal, the outcome you have asked for. And there is a loop: the agent takes a step, looks at the result and decides on the next step until the goal is met or it gets stuck.

That loop is what separates an agent from an assistant. Ask an assistant to find overdue invoices and it will explain how. Ask an agent and it will query the finance system, compile the list, draft the reminders and, if permitted, send them.

The tools are where the value and the risk both live. An agent with read-only access to a knowledge base is low risk. An agent that can issue refunds, change user accounts or push code to production needs the same care you would apply to a new employee with the same access.

Agents are not magic. They can misread instructions, choose the wrong tool, loop without progress or report success when the job is only half done. They work best on tasks where the steps are fairly predictable, the result can be checked and a mistake can be caught and reversed.

The practical question is therefore not whether to use agents, but which jobs, with which tools, at what level of autonomy. The rest of this playbook is about answering that question with confidence.

The agent loop

How an agent works through a task

Every agent, however sophisticated, repeats a version of this cycle until the job is done.

Understand the goal

The agent reads the request, the instructions it has been given and any context such as documents or ticket history.

Plan the next step

It decides what to do next: search, read, calculate, update a record or ask a person for help.

Use a tool

It calls one of the tools it has been granted, within the permissions that tool allows.

Check the result

It reads what came back and judges whether it is closer to the goal or needs another approach.

Finish or hand over

It completes the task and reports what it did, or stops and passes the work to a person with a summary.
Good agents know when to stop. Build in clear hand-over points so an agent asks rather than guesses.

Where agents help today

Six jobs agents already do well

Agents are strongest on multi-step work that follows a recognisable pattern and ends in something a person can check.

Research and triage

Gathering information from several sources, sorting incoming requests and routing them to the right team with a summary.

Data entry and updates

Reading emails, forms or documents and updating the CRM, finance or HR system, with exceptions flagged for review.

Coding and IT operations

Writing and testing code changes, investigating alerts, gathering diagnostics and running approved fixes from a runbook.

Customer service workflows

Looking up orders, checking policy, drafting replies and completing routine actions such as rebooking or resending documents.
If a capable new starter could do the task from a written procedure, an agent may be able to do it too, with the same supervision.

Guardrails

Five guardrails for every agent

These apply whatever platform you use. They are the agent equivalent of good access management.
01
Least privilege
Grant only the tools and data the task needs. Read-only by default, with write access added deliberately and scoped tightly.
02
Human approval at the moments that matter
Payments, deletions, external messages and changes to access go to a person first. Make approval quick so it is not bypassed.
03
A full audit trail
Log every tool call, input and result, under an identity that clearly shows it was the agent. You need to know what happened and why.
04
Test before trust
Run the agent on realistic cases, including awkward and hostile ones, before it touches live work. Retest after every change.
05
A clear off switch
Anyone responsible must be able to pause the agent instantly, and there must be a manual fallback for the work it does.

Untrusted content

Prompt injection: when the data gives the orders

If an agent reads content you do not control, assume someone will eventually try to give it instructions.

Agents read things: emails, web pages, documents, tickets, chat messages. The model behind the agent cannot always tell the difference between content it should process and instructions it should follow. That opens a door called prompt injection, where text hidden in a document or web page tries to redirect the agent.

A simple example: an agent summarising inbound emails meets a message containing hidden text telling it to forward the mailbox contents to an outside address. If the agent has permission to send email, there is a real risk it tries. AI providers are working hard on defences, but no one currently claims the problem is fully solved.

The most reliable protection is not clever prompting. It is design. Keep agents that read untrusted content away from sensitive actions, or put a human approval step between them. Limit where an agent can send data. Do not combine access to private data, exposure to untrusted content and the ability to communicate externally in one agent unless there is a strong control in the middle.

Connecting agents to tools is getting easier. The Model Context Protocol (MCP) is an open standard, originally introduced by Anthropic, that gives AI applications a common way to connect to tools and data sources. It is now supported by many AI tools and platforms, and many software vendors offer MCP connectors for their products.

Standards like MCP are welcome because they reduce custom integration work. But each connector is still a piece of software with access to your systems. Treat it like any other integration: know who built it, review what it can do, approve it centrally and keep a list of what is connected to what.

01

Permissions and least privilege

Most agent incidents are permission problems. Get the access model right and most other risks shrink with it.
Identity
Give each agent its own named account or service identity, never a person's login, so actions are traceable and access can be revoked cleanly.
Scope
List the exact tools and actions the task needs. Prefer narrow tools, such as update this field, over broad ones, such as run any command.
Limits
Set boundaries in the system, not just in the prompt: value caps, record types, rate limits and approved recipients.
Review
Recertify agent access on the same cycle as staff access, and remove tools that are no longer used.
Owner
IT or security, with the business process owner
Bring this to the monthly review, with a date for each action.

Going live

Six steps from idea to trusted agent

A deliberate path that builds evidence at each stage, so autonomy is earned rather than assumed.
01

Name the job and the owner

Write down the task, the expected output and the person accountable for the agent's work.
02

Map tools and permissions

List every system it touches and the minimum access needed. Get security sign-off.
03

Build a test set

Collect realistic cases, including edge cases and deliberate attempts to mislead it.
04

Run in suggest mode

Let it propose actions on live work while people compare its choices with their own.
05

Raise autonomy in steps

Move to approval, then to limits, only when the results justify it.
06

Monitor and review

Check logs, error rates and feedback regularly. Retest after any change to model, tools or instructions.
Remember
Ownership does not transfer to the agent. Every agent needs a named person who answers for what it does.

Glossary

Words worth knowing

Agent
An AI system that uses tools to take a series of actions towards a goal.
Tool
A capability an agent can call, such as search, read a file or update a record.
Autonomy
How much an agent may do without a person approving each step.
Least privilege
Giving an agent only the access its task needs, and no more.
Human in the loop
A person reviews or approves an agent's action before it takes effect.
Audit log
A record of every action an agent took, with inputs and results.
Prompt injection
Hidden or malicious instructions in content an agent reads, aiming to redirect it.
MCP
Model Context Protocol, an open standard for connecting AI applications to tools and data.
Connector
An integration that gives an assistant or agent access to another system.
Runbook
A written procedure for a routine technical task, often a safe starting point for agents.
Sandbox
An isolated environment where an agent can be tested without touching live systems.
