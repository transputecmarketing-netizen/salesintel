What happened

On 21 October a backdoored version of LiteLLM, a widely used gateway that sits between applications and AI providers, was published to PyPI and Docker. It stole cloud keys, tokens and the AI provider keys the gateway holds. Days earlier, OpenCode lost stored provider keys to an intruder, and researchers reported that coding agents had been posting internal screenshots to public repositories.1,2,4,5

What it shows

AI tools concentrate secrets. A gateway holds every provider key; a coding agent holds your repository; an aggregator holds your prompts. One unrotated key, one broad token or one unbriefed agent is enough.

Our view: treat AI plumbing as production infrastructure with a named owner, scoped credentials and a rotation date. The same discipline as any other system that holds keys.

Five moves
Inventory AI tools and keys · Rotate on exposure, always · Pin and verify what you install · Scope every token · Brief your agents

How it unfolded.

Earlier

A key is committed

A repository once contained the master key of an experimental internal agent platform. The commit was overwritten. The key was never revoked.1

10 Oct

The key is used

The attacker uses it to extract a GitHub CLI token belonging to an organisation owner. The token was not scoped down and not tied to a service account.1

Before 21 Oct

Quiet escalation

Throwaway CI workflows harvest more tokens, including two engineers'. The release workflow is repointed to a lookalike repository with a hyphen in its name.1

19 Oct

Approvals loosened

Release permissions are relaxed so that any two engineers can trigger and approve a release.1

21 Oct

The release

Version 1.107.0 goes out to PyPI and to Docker tags. Security firms detect it within about six minutes; packages are removed within hours.1,3

23–24 Oct

The record is corrected

LiteLLM publishes the attack chain on 23 October. Earlier theories, about gateway logs or a leaked coding-tool token, were not how the attacker got in. Clean releases resume on 24 October.1,2

What the payload did

The malicious release added files that Python runs at start-up, so it executed on any Python launch on an affected host, even if LiteLLM itself was never imported. It stole credentials and fetched code from a remote server every hour.2

Use of stolen keys

Datadog saw no second-stage payload in the wild. Wiz reported that stolen AWS credentials were tested starting about four and a half hours after exfiltration, consistent with abusing them to run AI workloads.2,6

OpenCode Console · 16–17 Oct
Mostly solid

Attackers entered an older system overnight. Provider API keys stored by 1.4% of Console users, those who had linked OpenAI, Anthropic or Google, were exposed and used to run up charges. Some users reported more than $1,700 overnight; those figures are user reports. Anthropic and Google blocked keys; OpenAI said it worked with OpenCode on access and refunds.4,7

Caveat. OpenCode called it a large-scale distillation attack. Reporters note it did not explain how, and sceptics call it a plain breach. The entry route is undisclosed.

PixelLeak · Reported 1 Oct
Single source

Glow reports AI coding agents that could not attach images to pull requests in private repositories worked around it by posting screenshots to public ones, often under the developer's personal account. Over 13,000 images from 300+ organisations across 900+ repositories; 93% were under personal accounts.5,8

Caveat. Vendor research that promotes its own controls. No organisations are named; Glow's page metadata and Tom's Hardware give different dates.

302.ai storage · Found early Aug
Single source

Cybernews reports an unencrypted, password-less cloud storage bucket linked to an AI aggregator holding 17.6 million files and 22.72 TB, including roughly 500 GB of chat logs, prompts and responses. It was locked down about a month later. The news broke on 22 October.9

Caveat. No vendor statement and no evidence of third-party access. The headline says 18 million files; the body says 17.6 million. We use the body.

One pattern, four times.

Strip away the AI vocabulary and each incident is a familiar failure: access that was wider, older or more open than anyone intended.

IncidentThe failureThe control that helps
LiteLLMOne unrevoked key; broad token; relaxed release approvalsRevoke on exposure. Scope tokens. Two-person release review that cannot be relaxed quietly.
OpenCodeProvider keys stored in a system that was breachedShort-lived, spend-capped keys. Alerts on unusual spend. Retire old systems.
PixelLeakAgents given a workaround nobody anticipatedTell agents where they may not write. Block public repos for sensitive projects. Review what they publish.
302.aiStorage open to the internetPrivate by default. Treat chat logs as sensitive data.
Our view
New technology does not need new principles. It needs the old ones applied to a place nobody was looking.

04 · What to do

Eight habits.
None of them are new.

Mapped to the plays in The Resilience Playbook, so each has an owner and a test.

Know
List every AI tool, gateway, agent and key in use. Name an owner for each.
Play 04
Rotate
Revoke a secret the moment it is exposed. Deleting a commit is not revocation.
Play 02
Pin
Pin dependencies and verify them. Delay adopting brand-new releases for production.
Play 05
Scope
Short-lived, least-privilege tokens. No organisation-owner tokens in everyday tooling.
Play 02
Cap
Spend limits and alerts on every AI provider key.
Play 04
Gate
Release approvals that cannot be relaxed without a second person noticing.
Play 05
Brief
Tell coding agents where they may and may not write, and review what they publish.
Play 04
Rehearse
Practise a leaked-key day: who rotates what, in what order, within an hour.
