What happened

Two memory-safety flaws in PHP itself, rated 9.2 out of 10, let an unauthenticated attacker run code on a server that handles web requests. They sit beneath WordPress, Drupal, Joomla, Magento and thousands of custom sites. Attacks were recorded four days before the fix. Details leaked hours before it. By 26 October CISA listed both as exploited.1,3,4

Banks, retailers, hospitals and some government bodies took services offline to patch, according to TechCrunch.4

What it shows

The window between a flaw becoming known and being used is now measured in hours. A patch that exists is not a patch that is installed: running processes keep the vulnerable code until restarted, and most exposed PHP runs on branches with no official fix.2,3

Our view: the organisations that coped best were not the best defended. They were the ones that already knew where PHP ran and who owned it.

Four actions
Find every PHP install · Patch and restart, then rebuild images · Look back to 17 October for signs of compromise · Rotate what may have leaked

Two bugs, in plain English.

Both are memory-safety flaws in how PHP starts, fails and cleans up a request. Neither needs a password or a click.

CVE-2026-109618

The out-of-memory bug

1An attacker sends a crafted multipart request, the kind used for forms and file uploads.
2PHP runs out of memory part-way through setting up the request, even when the size looks within limits.
3PHP abandons the request, leaving internal data half-built.
4Clean-up runs anyway and uses the invalid data. Memory is corrupted.
5In Apache mod_php this happens before any of the website's own code runs.
CVE-2026-109619

The stale-state bug

1A worker process handles many requests in turn, and keeps some state between them.
2At the end of one request, a pointer still refers to memory that has been freed.
3A fatal error or timeout interrupts the clean-up that would have reset it.
4The next request on the same worker reads the stale value, including through session upload progress, which is on by default.
5Freed memory is reused. Code runs.
Why it matters

Because the flaw is in PHP rather than in a plugin, a site can have flawless application code and still be exposed. Wiz also showed that the memory-disclosure side can leak passwords, tokens, API keys and certificates from other requests, with no code execution at all.3

Sources: PHP advisories as summarised by Rapid7 and Recorded Future. The session upload progress feature has existed since PHP 5.4.0.

Before the world knew.

19 Aug

Discovery

Wiz Research finds the first flaw using AI-assisted tools. Within two days it confirms unauthenticated code execution on Drupal, then WordPress.3

24 Aug

Reported to PHP

Wiz privately reports the flaws to the PHP security team, starting coordinated disclosure. Calif and OpenAI are credited alongside Wiz.3

Fixes begin

The PHP security team acknowledges the reports and starts building coordinated fixes. Large hosts and Linux distributions later receive early access under embargo.3,4

17 Oct

First recorded attack

Amazon's MadPot honeypots log an exploitation attempt, four days before public disclosure. It is unclear how the attacker knew.2

20 Oct

A warning, without details

PHP announces an out-of-band release for 21 October at 14:00 UTC and withholds technical detail. watchTowr says it has reproduced CVE-2026-109618.3

Sources differ

Recorded Future dates the discovery to August 2026. TechCrunch reports the bugs were first noticed in 2024 and judged unexploitable until recently. We follow the dated timeline; the difference does not change what to do.

Five rungs of evidence.

Early headlines said everything from “nothing seen” to “the internet is on fire”. Both were true at different rungs. Here is how to read the claims.

Catalogued

Rapid7, Tenable

CISA adds both CVEs to KEV on 26 October, evidence of active exploitation. Federal deadline 29 October.

Observed succeeding

Tenable

Shells ran attacker commands on three honeypots (PHP 8.4.26). Trail of Bits shows working exploits on MediaWiki, Symfony, Laravel and phpBB.

Reproduced in the lab

Recorded Future

watchTowr reproduced both. Wiz demonstrated code execution on WordPress, Drupal and Joomla.

Attempted

Tenable, TechCrunch

Amazon (17 Oct), Patchstack's hosts and Cloudflare (21 Oct) saw attacks. Cloudflare later reported an exponential rise in attempts.

Warned

Recorded Future

PHP announces an emergency release on 20 October with details withheld.

Caution

Rapid7 found the early public proofs of concept worked only in narrow lab conditions and treated the difficulty as a window to patch rather than a reason to delay. Days later, working exploits were confirmed. Reliable exploitation is a matter of time.1

05 · The response

Who did what.

Most of the system worked. The weak points were hours, restarts and the long tail of systems nobody was watching.

Maintainers

The PHP Foundation ran a coordinated disclosure, giving large hosts and Linux distributions early access under embargo, then published fixes on 21 October.4

Platforms

Cloudflare put stopgap firewall rules in front of PHP sites for every customer, free tier included, and said plainly that they were only a stopgap.3

Governments

CISA listed both CVEs as exploited, set 29 October as the federal deadline and required forensic triage. CERT-EU advised isolating internet-facing PHP apps that cannot be updated. The UK NCSC reportedly advised updating or taking systems offline, per BleepingComputer.1,2,6

Businesses

Banks, retailers, gaming sites, online stores, hospitals and some government agencies took servers offline to apply patches, TechCrunch reported.4

Our view

Taking a site offline is a legitimate control, not a failure. The organisations that could make that call in an hour had already decided who is allowed to make it, and what a day without the site costs.

Sources: 1 Rapid7. 2 Tenable (CERT-EU). 3 Recorded Future; Tenable. 4 TechCrunch. 6 BleepingComputer, for the UK NCSC advice; we could not retrieve the NCSC's own text.

Six traps that
made patching hard.

01

Updated is not patched

Installing a new package does not fix processes already running. PHP-FPM and Apache keep the vulnerable code in memory until restarted. Google Cloud's guidance, with Mandiant, also advises capturing worker memory from probed servers before restarting.2

02

Containers keep the old image

Patching a running container leaves the image exposed. Rebuild and redeploy.7

03

End of life, no fix

PHP 8.1 and older get minimal source backports only. Remi's repository did not update on 21 October; users were told to switch to distribution packages or build from source.1

04

A regression in the fix

PHP 8.4.27 and 8.5.12 can crash some applications that use SimpleXML (php-src issue 24488). It comes from a separate garbage-collector change, not the security patches.2

05

More after the patch

CVE-2026-115560 had no patch on 23 October. On Windows, builds were refreshed on 26 October for a bundled Brotli flaw, CVE-2026-111497.1,2

06

PHP you did not install

PHP also sits in developer tools and in components used by routers, storage devices, firewalls and VPNs. Those need their vendors to ship updates.4

Sources: 1 Rapid7. 2 Tenable. 4 TechCrunch. 7 Aikido.

Chapter 06 · The AI question

Found with help from AI.
Not found by it alone.

What was reported

Wiz and Calif both say they used AI models in the research. Calif's write-up is blunt about the limits: “No model is simply capable of unearthing ‘all bugs’ with simple prompts. At least for now.” The bulk of the work relied on researchers who knew PHP's code and exploitation history well.3,4

Discovery was part of OpenAI and Wiz's Hack the Planet initiative.4

Why it changes planning

Old, widely used, memory-unsafe software is the likeliest place for the next discovery. TechCrunch cites the NSA's estimate that around 75% of actively exploited vulnerabilities abuse memory-related flaws.4

If finding flaws gets cheaper for defenders, it gets cheaper for everyone. The honest planning assumption is shorter windows, not longer ones.

Not the first PHP warning

Before PHP2Shell, CISA's catalogue already held three PHP flaws. CVE-2024-4577 (PHP-CGI) and CVE-2019-11043 (PHP-FPM) are both known to have been used in ransomware campaigns. The third, CVE-2012-1823, is the flaw CVE-2024-4577 later bypassed.2

Sources: 2 Tenable. 3 Recorded Future. 4 TechCrunch.

A 72-hour runbook.

Illustrative, built from the vendor, CISA and researcher guidance in the sources. Adapt it to your estate.

First hour
  • Name an incident owner and a decision-maker for taking sites offline.
  • Pull the asset list: every web server, container image and appliance that runs PHP.
  • Rank by internet exposure; mod_php first.
Hours 1–24
  • Apply vendor packages or the fixed versions. Restart every PHP process. Rebuild images.
  • Where you cannot patch: isolate, or take offline. Treat a web firewall as a stopgap.
  • Apply PHP's interim settings where they fit, and check nothing restores a finite memory limit.
Hours 24–72
  • Look back to 17 October in web, application and endpoint logs.
  • Watch for odd multipart requests, PHP worker crashes and unexpected commands.
  • Absence of log entries is not proof of safety.
Days 3–30
  • Rotate secrets and keys that a PHP worker could reach.
  • Move end-of-life branches onto supported releases.
  • Write down what slowed you, and fix it.
Sources: Rapid7; Tenable; Recorded Future recommendations. This runbook is illustrative and is not a substitute for a vendor advisory.

Six questions for your
IT provider, today.

A good answer is specific, quick and written down. A vague one is also an answer.

01
“Do we know every place PHP runs, including inside appliances and containers? Show me the list.”
02
“How many of our PHP installs are on a branch with no official fixes?”
03
“How quickly can we patch and restart a critical, internet-facing system? Has it been tested?”
04
“Who can decide to take a site offline, and what does an hour of that cost?”
05
“Which secrets could a compromised PHP worker reach, and how fast can we rotate them?”
06
“Who tells us about a supplier's incident, and how quickly, in writing?”
Playbook

These questions map onto plays 01, 03 and 05 of The Resilience Playbook: map what matters, rehearse recovery, know your suppliers.
